# 認識遅延の経路監査（2026-11-03）

## 結論

認識サービスだけが原因と断定しない。providerMsはWorkersのAI.run開始から解決・例外までの経過時間であり、SDK・通信・提供元の待機・音声解読・VAD・推論・応答解析を分解できない。こちらが選ぶ入力形式・モデル設定の影響も含み得る。

## 実装と観測の対応

- 端末：PCM区間化 → WAV変換 → 認証 → 同時枠 → fetch → HTTP応答解析 → 先行区間との順序調整 → 認識出力フィルター・結合 → 翻訳。順序待ちはHTTP計測の後で別記録。先行音声が遅い場合は後続も表示待ちになる。
- サーバー：認証 → WAV/音声エネルギー検査 → base64化 → 予算確保 → AI.run → 予算精算 → 言語・品質判定 → 応答。providerMsは予算確保・精算を含まず、base64化も開始前。
- 自動日英の短区間認識ではcandidatesがあるため、旧Whisperへの自動フォールバックは行わない。manual指定言語では入力・モデル不適合時に旧モデルを使う可能性がある。全方式で常に1推論とは断定しない。
- 例：1.86秒音声のHTTP11306ms、サーバー合計11102ms、AI.run10995ms、認証0ms、予算確保82ms、精算25ms、順序待ちは数ms。これについて鍵取得や端末待ちが主因という証拠はない。各区間は重なるため全指標の単純合計はしない。
- 別の利用には順序待ち5210msの記録があり、常に端末側の待ちがないとも言えない。前の区間との意味・順序維持をせずに応答順表示へ変更すると、否定や続きの文を壊す危険がある。

## こちら側で修正した点

認証公開鍵の初回ダウンロードが同時要求で重複し得たため共有する。鍵の暗号オブジェクトも再利用する。署名検証とトークンの各条件は要求ごとに実行する。許可OriginのCORS事前確認を600秒再利用できるようにする。どちらも実回線での短縮量は未計測で、11秒待ちの解決とは表示しない。

## 未確定の点

AI.run内部の再試行・待ち行列・推論時間の内訳、端末のブラウザーにおける事前確認の実回数と往復時間、実教室の雑音下での精度は未計測。省略VADの初回15秒タイムアウトだけでVADの性能を一般化しない。モデル設定を変えた比較は、同一音声・交互順・失敗と期限超過を含めて評価する。


## 2026-11-03 端末側の処理と読込の再点検

web/serverのJavaScriptの相対importを機械的に走査し、会話の起動・音声区間送信・順序確定・辞書検索・翻訳・結果描画前の保存・管理画面読込を点検した。全機能の実環境検証を済ませたという意味ではない。

| 経路 | 確認内容と対応 |
| --- | --- |
| 初期モジュール読込 | 管理画面の集計・請求表示も起動時に読み込んでいた。明示操作時に遅延読込。同一ファイルの複数版URLはimport mapで統一。初期JS要求78→57。 |
| 利用記録保存 | 保存ごとに最大200件を解析・再変換していた。終了済み行だけ再利用し、現在行とチェックポイントの同期保存を維持。別タブ更新・容量失敗を試験。 |
| 診断記録 | 保存先が捨てるsessions引数のために全履歴を読む処理を4箇所から除去。分析画面に必要な参照は維持。 |
| 確認済み訳検索 | 現在キー不一致後に旧キーの別トランザクションを待っていた。1トランザクションで読み、現在キー優先と120ms期限は維持。実IndexedDBで旧形式の訳を取得。 |
| 音声区間・認識 | 3秒区切り、400msの末尾待ち、2件のHTTP並列、3件の総ジョブ枠を維持。2.4秒案は精度悪化で不採用のまま。 |
| 翻訳・順序 | 認識順序を確定する前の投機的な翻訳は追加しない。結合される文で余分な翻訳になり得る。提供元待ちと順序待ちは残る。 |
| 描画・再生 | 重複語尾の補完、発話があるときだけのローディング、再生後のマイク復帰を回帰試験する。画面描画完了や実際に耳に届く時刻の保証ではない。 |

実ブラウザーの合成履歴保存20回は267.1→182.6msで約84.5ms減った。人工JS通信遅延40msでの起動各2回は旧597〜632ms、新513〜550ms。会話ごとに100ms以上短くなったという結果ではなく、各経路の不要な処理を減らした測定である。認識サービス内部の待ち行列・推論・通信の分離と、利用者の実端末での短縮量は未計測。
