# iPhoneの読み上げ後のマイク入力復帰

ビルド: 20261029-ios-mic-recovery-1

観測では、読み上げ待機からの再開イベント後に認識要求がなく、手動OFF→ON後も送信が再開していなかった。旧記録に入力フレームとミュート状態はなく、原因は断定できない。

既存処理は、liveのままのMediaStreamTrackを再利用していた。WebKitには音声合成後にマイクがミュートのままになる報告があるため、iPhone/iPadの読み上げ後、およびミュートされた入力では入力を取り直す。手動OFF→ONも新しい入力を取得する。失敗時はOFF表示と操作案内を出す。

参照: https://bugs.webkit.org/show_bug.cgi?id=218815 （過去に修正済みとされ、後年の再現報告もある。今回と同じ原因であることの証明には使わない。）

入力取得後も、ON意図・操作世代・部屋・前面表示を検査する。OFF・退室・背景移動後には再開しない。取得中に新しい読み上げが始まった場合は、その読み上げ終了まで入力を待機する。

稼働通知が最初から来ない録音処理も期限内に検出する。通知はあるが入力フレームが3回連続でない場合も明示的に停止する。通常の無音は停止理由とせず、入力フレーム数・信号フレーム数・ミュート状態を本文なしで区別して記録する。

検証: 単体・統合テスト、390×844・844×390・320×568でミュート継続を再現した読み上げ3回後の入力復帰、手動OFF/ON、取得失敗表示。実AudioContextとAudioWorkletで31秒の環境音から小さな発話へ移る試験。チャット・復旧・上限の既存テスト。物理iPhoneでの試験は含まない。

既存モデル・単価・予算上限は変更しない。入力の取り直しだけでAIを呼ばず、録音の再送もしない。
